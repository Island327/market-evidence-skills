# 建设和维护知识库

目标是让另一位 Agent 能找到正确原文并给出有边界的答案，而不仅是搜到相似文字。先明确知识库服务的任务、读者、资料范围和更新责任，再选择文件夹、数据库、搜索索引或 RAG 平台；方法不绑定具体后端。

## 四层内容

| 层 | 记录什么 | 不能替代什么 |
| --- | --- | --- |
| 原始来源 | 不改动的文件字节、来源、哈希、取得时间、使用权限 | 不因上传成功就算已验证 |
| 结构化提取 | 页、段、表、条款、型号、数值、单位和限定条件 | OCR 或模型提取不自动成为事实 |
| 证据与事实 | 具体主张、原文位置、适用范围、审查状态、冲突和版本关系 | 摘要不是另一套权威事实源 |
| 检索与应用 | 索引、问答、偏离表、引用及报告 | 检索得分不是可信度或合规分数 |

可从 CSV 目录和普通文件开始。数据量、权限和并发需要时再迁移到数据库，保留稳定的来源 ID 与证据 ID。

## 接收资料

核对文件实际内容和文件类型，记录来源人/机构的角色而非只靠文件名。区分产品手册、正式规格、注册资料、营销宣传、项目需求、投标响应、合同、图片和人工说明。项目要求不是产品能力；投标人自述也不自动等于原厂证据。

先明确是本次任务使用、候选收录还是正式发布。尊重“仅这次使用”。按现有授权取必要原件，不因为有共享链接就批量下载整个目录。

用内容哈希识别完全相同的文件，可复用其解析结果；同文件名不代表同内容，同内容的另一个来源可追加来源关系。来源权限不同不能因去重而扩大读者范围。重复处理已有作业时先读作业状态，沿用作业标识。

## 保留结构与版本

来源目录至少记录 `source_id`、标题、相对存储位置或授权访问地址、文档类型、版本/发布日期、SHA-256、适用型号/配置/市场、取得时间、访问范围和状态。见 [来源目录模板](../assets/templates/source-register.csv)。

保留原件；提取后的文本是派生物。页码需要区分 PDF 物理页和文档印刷页。扫描件留 OCR 不确定区域，抽查数字、小数点、比较符号和单位。表格跨页时保留表头、脚注、合并单元格的含义，避免一条参数丢掉配置前提。

切块围绕条款、表格或小节，保存父块/邻块关系。检索到“支持”时还要看前后的型号范围、选配项和否定条件。精确型号和错误码优先精确匹配，再用关键词或语义检索扩展；不要把相近型号合并成一个型号。

新旧版本并存，以 `supersedes` 记录取代关系及适用范围。新手册可能只覆盖某市场或配置，不应仅凭日期抹掉其他适用版本。增补文件只变更明确涉及的条款。来源撤回或更正时标记受影响事实，并使下游报告可追踪到需要更新的结论。

## 提取与核实证据

每条证据保留短原文、来源 ID、版本、具体位置、对象和限制，另列规范化值/单位与解释。证据目录见 [证据条目模板](../assets/templates/claim-register.csv)。

建议状态可按团队调整：`candidate` 待核、`verified` 已核、`conflicted` 冲突、`superseded` 被后续版本取代。不要让模型置信分直接把候选提升为已核。关键事实要能从引用回读原文。

冲突先检查对象、时间、地区、配置和条款条件是否不同。确有冲突时展示两条来源和差异，按本任务明确的权威规则裁决；不取平均值或选“更好看”的数字。动态事实需保留核验日期，尤其不能用历史证件的起止日期推断今天是否有效、已续证或适用于某次投标。

## 验证检索是否有用

选少量有代表性的实际问题测试：精确型号、同系列易混型号、跨页参数、选配条件、否定条款、旧版本、无答案、无权限资料。检查是否找对原文、带回必要上下文，是否在缺证时明确不知道。命中率只反映检索，答案是否被证据支持要另查。

入库状态使用可观察阶段：已接收、已解析、待核、已索引、已发布、失败。已索引不一定所有读者都可读；核对实际权限下的检索结果。长任务保留断点、错误和可重试范围，不承诺未配置的自动通知。

## 更新与交付

只对新文件、变更证据或失败步骤增量处理；已核且没有新证据的来源不重复处理。先在候选区验证，再按现有发布权限发布，保留可恢复前一版本。具体审批角色、保存期限和更新频率由使用者配置。

交付来源目录、证据条目、待核/冲突清单、版本变化摘要和检索验证结果。公开示例只用合成数据或已明确许可的公开资料；索引和摘要也要遵守原资料的权限。
